# Panel question map and moderator kit

Use for a moderated panel, fireside chat or roundtable discussion. The moderator owns this document; panelists see only their own questions and the run of show.

## 1. Inputs to collect (ask only what the chat, the event page or the user's files do not already say)
- Event name, date, city and time zone, room or format (in person, online, hybrid). Check the date and weekday with `scripts/text_check.py date YYYY-MM-DD Weekday`.
- The session length and the organiser's rules (self introduction length, pitch rules, audience questions).
- The theme in one sentence, and the audience by role and sector.
- Each panelist by role, company type and the angle they can speak to. Names only if the user gives them; never research private details.
- What each panelist has already said in public (talks, posts, articles) if the user wants it used. Public professional statements only.
- Topics that are off limits for each panelist or their employer.

## 2. Run of show table
| Time | Duration | Segment | Owner | Notes |
|---|---|---|---|---|
Fill it for the user's session length. Typical segments: moderator opening, panelist self introductions (short, no pitch), two to four topic blocks, a lightning round, audience questions, moderator close. Segment durations must add up to the session length; show the sum.

## 3. The question block (one per question)
Each main question runs in five parts. Write all five for every question.
1. Context: the situation the audience recognises, in one or two sentences.
2. Tension: the trade-off or disagreement that makes the question worth asking.
3. A concrete example: a real case the panelist can tell. If the panelist has not supplied one, write "[Panelist to supply: one example from their own work, public or cleared by their employer]". Never invent one.
4. A metric: the measure that shows whether the approach worked. If unknown, "[Panelist to supply: the measure they used]".
5. The takeaway: the one thing the audience should do or check.

Add for each question: why it matters to this audience, the primary voice (which panelist answers first), the reasoning path you expect, two moderator follow-up prompts, and the metric to listen for.

## 4. One example and one failure per topic
"What not to do" matters as much as "what to do". For every topic block, plan one example of what worked and one failure (what went wrong, why, what changed). The failure must come from a panelist's own experience or be framed as a general pattern; never attribute a failure to a named company. A failure from a panelist's own employer is an internal practice: it passes the confidentiality filter in section 8 and is never relabelled a general pattern to get past it.

## 5. Lightning round
One prompt per panelist, answered in a few sentences: "Name the use case, the tool category (not the vendor), the metric, and the first step." Protect this round and the audience questions when time runs short; cut a topic block before cutting these.

## 6. Audience question shape
Ask panelists to answer audience questions as: context, one concrete step, one metric, a pointer (where to learn more). Plan for at least two audience questions; prepare two seed questions in case the room is quiet.

## 7. Moderator rules
- No vendor pitches and no product promotion by panelists or the moderator.
- Short self introductions; the moderator enforces the time.
- Credit a panelist's framework or model by name to its owner. Never present it as the moderator's or the host company's.
- No generic advice that would fit any industry; steer back to the panelist's own case.
- The moderator's own replies trace to these prep notes.

## 8. Confidentiality filter
Before the kit goes to anyone, check every example and metric: if it describes an internal practice of a panelist's current employer, it stays out of the kit, or is marked "[Panelist to confirm: public or cleared by their employer]", until the panelist confirms it is public or cleared by their employer. Mark each item held back "[held back for confidentiality]" in the moderator's copy only.

## 9. Sector tuning
Use the vocabulary of the audience's sector, and ask the user to confirm it:
- Logistics tech: shippers, carriers, lanes, loads, exceptions, dwell time, on time delivery, visibility, yard, last mile.
- Fintech: banks, lenders, issuers, merchants, compliance, risk, fraud, onboarding, collections, regulators.
- Telecom: operators, enterprise customers, backhaul, rollout, network capacity, spectrum, field operations, uptime.
Never add a statistic, market size or benchmark for the sector without a source the user gives or a page fetched in the session.
