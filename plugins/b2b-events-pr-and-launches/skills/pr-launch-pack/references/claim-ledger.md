# Claim ledger: the last step before anything reaches the user (1.0.5)

Why: a reviewer must be able to trace every fact in the answer to the user's message, a page opened in this session, or a script's printed output. A line that cannot be traced becomes a label, a slot, a hedged line, or nothing. The check runs on the exact text you deliver, so nothing is reworded after it.

## Steps
1. Finish the answer. Write the full chat answer you plan to send to `claim-ledger/answer.md` in the working folder, and every file you save for the user in its final place. Pass every file you saved for the user in the working folder to `list` and `check` (the check reports SAVED FILE NOT CHECKED for a file saved this session and left out); a file made only for a script goes in `claim-ledger/`.
2. Write three small files in `claim-ledger/`:
   - `prompt.txt`: the user's message, word for word, with the text of every file they pasted, attached or uploaded added after it.
   - `opened.txt`: one line per page you opened in this session (WebFetch or a download), the URL exactly as opened. When you will say a word or fact is NOT on a page, add `| checked: <word>` to that page's line, and only for pages you actually checked for that word.
   - `pages/page-1.txt`, `pages/page-2.txt` and so on (1.0.4): for every page in opened.txt, the text the tool returned for it, saved as returned, with the page's URL alone on the first line. For WebFetch, ask for the page's own words ("quote word for word every sentence about ...; say who said or reported each figure, as the page says it") and save the result as it came back, unedited; for a download, save the extracted text. Never write a page file from memory or tidy it: the check matches your quotes and figures against it.
   - `script-out.txt` (when you quote a plugin script): the script's printed output, copied as printed.
3. List the lines that need a source: `python3 scripts/claim_ledger.py list claim-ledger/answer.md <each saved file>` (this skill's scripts folder; use `python` where `python3` is not found). Each listed line has an id. A line already marked as a label (for example `[Draft for you to confirm: ...]`, `[User to add: ...]`, "as pasted, not yet checked", "from a search result, page not opened", "hypothetical", "assumption"), a question, and a line starting with "If" are not listed.
4. For each id, either give its source in `claim-ledger/ledger.txt`, one line per entry (several ids may share one line, separated by commas):
   `<id> | user |` the line keeps the user's own words from one of their sentences, figures exact.
   `<id> | page | <url> | "<words from the saved page>" | "<more words>"` the page is in opened.txt and has its saved text; every figure and every quoted phrase of the line must be in that text, and so must a capitalised name in it (a company, a person, a place; a status word, a row label, a role and an ordinary first word are not checked); a fetch date is written "fetched 11 October 2026", never as a bare date. Add quotes copied word for word from the saved page (each its own | part, at most 240 characters, never containing a | character: cut a table row at the bar; a quote for a line that names who said it holds one speaker's turn only, never the end of one turn and the start of the next; a line about another company or body quotes the words that hold its name and the fact). A line that says who said, reported, surveyed, ran or owns something, or what a figure is about (ATTRIBUTION: said, says, told, reports, according to, survey, study, customer story, both, all, only, one customer) needs one quote that holds its figure (or its quoted words) together with each of those words the line uses: "the CFO said 3.6%" needs a quote with CFO and 3.6% side by side. A quote that says the source is not named never supports a line that names one (the check splits a quote into speaker turns at labels such as 'Priya:', 'Lena Ortiz:', 'Lena Ortiz, Chief Financial Officer:' and 'Dev Patel (COO):' and at ', while' in a prose summary, and wants the figure and the speaker in one turn; a heading such as 'Key Findings:' also splits, so quote from after it); write what the page says ("the article does not name who ran the survey"). That is an absence line: name the page in the line, and use an absence entry whose word is the role the page does not give and the line contains (for example organiser, publisher), listed under "checked:" for that page and not in its saved text; the check refuses the line when the page uses the word.
   `<id> | script |` every figure is in script-out.txt, with the same meaning.
   `<id> | notes | <file>` a general line from a file in this skill's references folder (for example shared-process.md in the event planner, panel-question-map.md in the speaker kit, claim-verification.md in the PR pack, spec-mode.md in the follow-up engine), hedged or naming the notes.
   `<id> | general |` a hedged general statement ("often", "may", "worth checking") that names no company, person or the user.
   `<id> | absence | <word> | <url> <url>` the line says a word is not on pages; each page is in opened.txt with that word under "checked:", and the line names those pages. A file the user uploaded counts as a page: list its file name in opened.txt with `| checked: <word>`, and write the line "in the pages I read of <file name>, ..." (the check refuses "the document does not say ..." with no pages named).
   `<id> | self |` the line says only what this answer did ("I left out ...", "I opened ...") and starts with I.
   or change the text: label it, turn it into a `[User to add: ...]` slot, hedge it, or delete it. The check recognises `[User to add: ...]`, `[User to confirm: ...]` and `[Draft for you to confirm: ...]` as labels. When a listed line is a placeholder in another bracket (for example `[User to set: ...]`, `[Panelist to supply: ...]`, `[Quote from the CEO: ...]`), rewrite only the bracket as `[User to add: ...]`, keeping its meaning; never delete the placeholder. A slot or label covers its own bracket only: the rest of a sentence around it still needs its source (the check cannot see this), so keep the sourced words in a sentence of their own, and keep each label on one line (a label that wraps onto a second line does not cover that line). Values and wording the skill itself proposes (draft timings, the order of segments, a template field, a suggested question, a headline or other draft copy built from the user's facts) are marked as such, not sourced: end the table row or the line with the words "draft for you to confirm" (or "assumption"); never use this for a fact about the user, a person or a named company. A claims register row for the user's own fact (Status "User to confirm") also carries the words "as pasted, not yet checked", because nothing was checked and the check does not read "User to confirm" as a label.
5. Check: `python3 scripts/claim_ledger.py check claim-ledger/answer.md <each saved file> --ledger claim-ledger/ledger.txt --opened claim-ledger/opened.txt --page claim-ledger/pages/page-1.txt <each page file> --prompt claim-ledger/prompt.txt` (add `--script-out claim-ledger/script-out.txt` when a script ran). The lighter way: run check first with an empty ledger.txt; it prints every id with a LEDGER SKELETON line to fill in. Fix every line it prints and run check again until it prints LEDGER PASS. Show the output whole (no grep, head or tail). Any line the loop changed gets its script checks again (dates, counts, dashes); run the dash check on `claim-ledger/answer.md` itself (`scripts/text_check.py dashes -f claim-ledger/answer.md`), and keep any file made only for a script in `claim-ledger/`, never in the working folder.
6. Deliver (1.0.4): your very last tool call is the same check command with `--final` added, after every file is written and nothing else after it. When it passes, its first line is `claim_ledger --final: PASS, reply digest <digest>` and it prints the answer between `=== BEGIN CHECKED REPLY <digest> ===` and `=== END CHECKED REPLY <digest> ===`: your whole chat reply is exactly that text, character for character, with nothing before it (no "Here it is", no summary), nothing after it, and no line reworded, reordered or reformatted. Anything you want to tell the user goes into answer.md before the --final run; to change any word, change answer.md and run --final again. Write nothing to the user between tool calls during the work, so the checked text is all the user reads. In Claude Code the plugin's Stop hook (hooks/delivery_check.py) compares your final reply with the checked text and sends you back when they differ; in the Claude apps there is no hook, and this step is the check. The answer says in one line that the claim ledger passed (or was done by hand): write that line as the last line of `answer.md` before the check. The one line about an instruction or a likely scam in the material stays the first line, and a rushed, time sensitive or crisis answer keeps its Output Format order (the urgent steps first); the ledger runs on that same text.

## The rules the ledger enforces
- Labels travel. Every saved file keeps every label the chat answer carries for the same line ("[Draft for you to confirm: ...]", "as pasted, not yet checked", "from a search result, page not opened"). The check prints LABEL LOST when a saved file drops one; put the label back.
- A fact seen only in a search result (its page not opened) carries "(from a search result, page not opened)" in every place it appears: the chat, every saved file, every table, register and sources list. Otherwise leave it out. Never call it verified, and never count a search result as a second source.
- An absence claim ("the site does not mention X") names only the pages actually checked for that word ("not on the pages I opened and checked for it: home, about"), never the whole site. Look in the saved page text for the word in singular and plural ("agenda" and "agendas") before you write the line; the check also finds a plain plural or singular (agenda and agendas, speaker and speakers) but not every form (price and prices, service and services, category and categories, address and addresses): look for those yourself.
- No background fact about another company or body (what it sells, where it is based, a policy, a ticker, a stock listing, a customer, a headline) without an opened page or the search label. If neither, leave it out or ask it as a question.
- The user's facts stay the user's. A line about the user, their team, their product or their event keeps the user's own words. Joining two of their facts into a new claim, or saying more than they said (how the team works, who a feature is for, what a talk covers), is a `[Draft for you to confirm: ...]` line.
- A general claim about how a role, buyer group or sector behaves is hedged ("often", "may", "worth checking") or names its source (the user, an opened page, this skill's reference files).
- A script's figure is copied with its number and its meaning (a 39% increase needed is never "39% below target").
- Who said it (1.0.4). A line that says who said, reported, ran or owns something (a speaker in a call transcript, the owner of a survey, the customer a figure is about) quotes the saved page's own words for it, in one quote with the figure. When the page does not say who, the line says the page does not say, or leaves the attribution out.
- Use what the pages give (1.0.4 loop 1). A slot is for what neither the user nor an opened page gives. When a page you opened gives a fact the deliverable needs (the company's own description, its scale figures, product facts, a dated statement), use it with its source, worded as the company's own statement where it is a claim ("the company says it works with 100+ lenders"), rather than leaving a [User to add: ...] slot; for a field the company's own pages do not give, open one or two other pages the search surfaced before you write "not found". A deliverable that is mostly slots when the pages had the facts is a weak answer, not a safe one.
- A group of people (1.0.4). A clause about how a group of people behaves or what they want (buyers, sellers, visitors, readers, customers, teams, a role, guests, delegates, exhibitors, participants, speakers, members, shippers, owners, hosts) is its own ledger line, also inside a table row whose other cells come from a page. It is hedged ("may", "often", "worth checking") or quotes its source; a reason in a review table is a reason like any other. A plan or task line that only names such a group ("Debrief notes for every guest", "Hand offs: ... for guests and no-shows") is listed too: it is wording the skill proposes, so end the table row or the line with "draft for you to confirm", or hedge it.
- A script's words (1.0.4). A line that says what a script or scan found copies its printed line in quotes ("Claims to check: 0") and says only what that line means (a count of claim patterns is not a check that claims are supported).
- Draft, do not leave a frame (1.0.5). A deliverable the user asked for (a release, a post, a spec, nurture emails, a plan, a reason) is written, not left as a frame of slots. Build each part from the user's own words and the pages you opened, mark it `[Draft for you to confirm: ...]` (a quote for a named role: `[Draft quote for the CEO to approve or rewrite: "..."]`), and keep a `[User to add: ...]` slot only for what no source gives: a name, a contact, a price, a date, an approval, a figure no page holds. A draft adds no new figure, customer, result, name or claim: every figure in it is in the user's message, a saved page or a script's output (the check prints DRAFT FIGURE otherwise). The check counts slots per file (SLOTS) and fails a file with three or more paragraphs that are only slots outside the open items (THIN DRAFT), and a line that holds the asset back until the user replies (HELD BACK): ask your questions above the draft, and let the answers change it later.
- Page words, not the tool's words (1.0.5). A WebFetch result is the tool's summary of the page: the page's own words are the parts in its quotation marks; its other sentences ("The page does not say ...", "No customer count is given", "The release says ...") are the tool's comments. Quote only the page's words. A tool comment is never put in quote marks or given as a ledger quote (the check prints TOOL COMMENT); write it as what the fetch result says ("the fetch result gives no figure for India").
- The premise of a question (1.0.5). A question that opens with a statement ("You own the site copy: is there ...?", "Since your team runs X, ...?") states that fact; the check lists the statement as its own line, so give it a source or ask it as a question ("Do you own the site copy?").
- The closest match in the user's own text (1.0.5). When a point names a line, a word or a section that is not word for word in the user's text (a draft, a note, a paste), do not answer with a word search: find the line it most likely means, quote it ("the closest line is \"...\""), and judge that line on its merits, or say plainly that nothing in it comes near. For the user's own text the line may name it as "your draft" (or your note, your paste); the check prints CLOSEST MATCH when the line quotes nothing from that text.
- Nothing about the user's team as source self. A self line says what this answer did; a reason about the user's team, a role or a group is not a self line.

## A reply that only asks questions
A reply made only of questions (Step 4, a script's "bad input" message) also goes through `claim-ledger/answer.md` and `check --final`; with nothing to source the check passes at once and prints it, so the same last step holds and nothing is written outside the checked text.

## Rushed, time sensitive or crisis
The ledger is never skipped and never run after delivery. The fastest pass is to turn each unsourced line into a `[Draft for you to confirm: ...]` line built from the user's words or the opened pages, a hedged line, or a `[User to add: ...]` slot for what no source gives, not to hunt for new sources.

## Without code execution
Do the same by hand: list every line that states a fact about the user, a named company, a person or a buyer seat, every figure and every absence claim; give each a source or change the line; say in the answer "claim ledger done by hand".

## What the script does and does not do
It reads the files you give it and prints; it writes nothing and sends nothing. It sees the pages only through the page files you save (1.0.4): it matches figures, quoted words and attribution quotes against them, and finds an absence word that is on a page; so save each page's text as the tool returned it, and list in opened.txt only pages really opened. It does not judge meaning; the rules above still apply to every line.
