# Press release and regional releases

## A. Inputs (ask only what is missing)
- The announcement in one sentence and why it matters now.
- The company's own description (boilerplate) from its page or the user.
- Who the release is for (trade press, business press, customers, investors) and the house style the user follows (for example AP style), if any.
- Quote sources by role, and whether each person will write their own quote or approve a draft.
- The facts, each with its source (they go through claim-verification.md first).
- Release date, embargo (with time zone), city for the dateline, media contact.

## B. Release structure
1. Headline: what happened, plainly, with no superlative unless verified. Count by script.
2. Subheadline: the supporting detail. Count by script.
3. Dateline: CITY, date (weekday checked by script if a weekday is written).
4. Lead paragraph: who, what, when, where, why, in third person and present tense.
5. Significance: what changes for the customers or the market, using verified facts only; who the product is for and what it does only as the user or an opened page says, otherwise "[User to add: ...]".
6. Quote 1 (company executive): by default a placeholder with the points it should cover:
   "[Quote from <role>: to be written or approved by them. Points to cover: <point 1>, <point 2>.]"
   Draft wording only if the user asks, always marked "DRAFT QUOTE FOR APPROVAL BY <role>", and never presented as said.
7. Supporting details: timeline, scope, availability, from the user or cited pages. No supporting statistic unless it is in the claims register as verified or confirmed; otherwise "[User to add: figure and source]".
8. Quote 2 (customer, partner or outside expert): placeholder as above, plus "[Customer approval needed]".
9. About the company: the boilerplate from the company's own page or the user, with its scale lines checked for date.
10. Media contact: "[User to add: media contact]". Never invent a name, email or phone.
11. Distribution notes for the user: target media list (the user's), embargo terms, supporting materials (images, fact sheet), and who sends it. The skill never sends or publishes anything.

No marketing jargon, no hype, no exclamation marks. Writing rules apply.

## C. Regional releases
Use when one announcement goes to several countries or regions.
1. Write the core release first, generalised so it is true everywhere.
2. Make one version per region. Keep the core facts the same. Local figures (local customers, local users, local prices, local regulators, local partners) stay placeholders for the local PR team: "[Local PR team to add: ...]".
3. Currency: ask which currency each region uses in the release; never convert a figure by guess.
4. Dateline city and date per region, with the weekday checked by script and the time zone for any embargo.
5. Headlines, subject lines and meta text per region are counted by script. Take the length limit from the user, the outlet or the platform's current guidance; if none is given, show the count and ask.
6. For a release in another language or script, count it by script (code points) and say that a fluent speaker must review it before release; never claim a translation is checked.
7. End with the open items per region: launch date, press contact, local figures.

## D. Email pitch and web page lines
- Email subject line and preview text: counted by script.
- Page title and meta description: counted by script; limits from the user or the platform's current guidance.
- Every line carries the same verified facts as the release.
